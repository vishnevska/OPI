Тема

Репозиторій проєкту: структура, історія та гілки

1. Мета роботи

Метою практичного заняття було навчитися створювати та структурувати Git-репозиторій проєкту, працювати з історією комітів і гілками, виконувати злиття, створювати та розв'язувати конфлікти злиття, а також безпечно скасовувати помилкові зміни.

У роботі використовувався проєкт CoffeeGo — мобільний застосунок для попереднього замовлення кави в мережі кав'ярень.

2. Репозиторій проєкту

Для виконання практичної роботи було використано Git-репозиторій проєкту CoffeeGo на GitHub:

https://github.com/vishnevska/OPI

Репозиторій містить документацію проєкту, базову структуру каталогів, файли налаштування Git та історію виконання практичної роботи.

Тип системи CoffeeGo — мобільний застосунок для iOS та Android.

Основні користувачі системи:

клієнт — створює та оплачує замовлення;

бариста — переглядає замовлення та змінює їх статус;

менеджер — контролює замовлення мережі кав'ярень.

3. Структура репозиторію

У репозиторії створено базову структуру:

OPI/
├── docs/
│   ├── board/
│   │   └── .gitkeep
│   ├── practical4/
│   │   └── README.md
│   └── requirements/
│       ├── SRS_CoffeeGo.md
│       └── requirements-analysis.md
├── src/
├── tests/
├── .gitattributes
├── .gitignore
└── README.md


Каталог docs/requirements/ використовується для технічної документації та аналізу вимог.

Каталог docs/practical4/ містить звіт цього практичного заняття.

Каталог docs/board/ призначений для матеріалів, пов'язаних із дошкою задач та плануванням.

Каталоги src/ і tests/ підготовлені для подальшої розробки програмного коду та автоматизованого тестування.

4. Файл .gitignore

Для репозиторію створено файл .gitignore.

Його призначення — не допускати потрапляння до Git тимчасових файлів, файлів IDE, локальних налаштувань та секретів.

Основні правила:

.DS_Store
Thumbs.db
.vscode/
.idea/
bin/
obj/
*.user
.env
appsettings.Development.json


Таким чином, до репозиторію не повинні потрапляти локальні налаштування середовища, секрети, тимчасові файли та службові файли майбутнього .NET-проєкту.

5. Файл .gitattributes

Файл .gitattributes використовується для визначення правил роботи Git із різними типами файлів.

Основний рядок:

* text=auto


використовується для автоматичної нормалізації кінців рядків.

Бінарними файлами позначено:

*.docx binary
*.pdf binary
*.png binary
*.jpg binary
*.jpeg binary


На відміну від .gitignore, файл .gitattributes не визначає, які файли потрібно ігнорувати. Він визначає атрибути вже відстежуваних файлів.

6. Історія комітів

Документація проєкту переносилася до репозиторію окремими логічними комітами.

Основні коміти:

a2b39f1 chore: додати базову структуру та правила Git
32331d1 docs: додати технічне завдання проєкту
1649e28 docs: оновити технічне завдання CoffeeGo
ddd5f5d docs: додати аналіз вимог CoffeeGo
522388d docs: уточнити структуру документації


Такий підхід робить історію репозиторію зрозумілою: за повідомленням коміту можна визначити, яка частина проєкту була змінена.

Після завершення роботи зміни були опубліковані на GitHub командою:

git push origin main

7. Робота з гілками та merge commit

Для виконання завдання зі злиттям було створено окрему гілку:

docs/update-readme


У цій гілці було внесено зміни до README.md.

Після створення гілки до main було додано окремий коміт. Через це гілка docs/update-readme і main мали різні вершини історії.

Після виконання:

git merge docs/update-readme


Git виконав тристороннє злиття та створив merge commit.

Таким чином, було продемонстровано ситуацію, коли fast-forward злиття неможливе, оскільки основна гілка вже має власний новий коміт після створення робочої гілки.

Після завершення роботи відпрацьовану гілку було видалено.

8. Створення та розв'язання конфлікту

Для демонстрації конфлікту було створено дві гілки:

feature/a
feature/b


В обох гілках було змінено один і той самий рядок у README.md, але різними способами.

Спочатку гілку feature/a було злито в main без конфлікту.

Після цього була виконана команда:

git merge feature/b


Git повідомив:

Auto-merging README.md
CONFLICT (content): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.


Причиною конфлікту було те, що дві гілки містили різні зміни одного й того самого фрагмента файлу.

У конфліктному файлі Git створює спеціальні маркери:

<<<<<<< HEAD
варіант із main
=======
варіант із feature/b
>>>>>>> feature/b


Потрібний варіант було обрано вручну, після чого маркери конфлікту було видалено.

Далі файл було додано до індексу:

git add README.md


та завершено злиття комітом.

Таким чином, було продемонстровано повний цикл виникнення, ручного розв'язання та завершення merge-конфлікту.

9. Скасування помилкового коміту

Для виконання завдання було навмисно створено помилковий коміт із тимчасовим файлом temp.txt.

Оскільки зміна була опублікована в репозиторії, для її скасування було використано підхід, який не переписує вже опубліковану історію.

Помилкову зміну було скасовано, після чого актуальний стан репозиторію було перевірено за допомогою:

git status


Результат:

On branch main
Your branch is up to date with 'origin/main'.

nothing to commit, working tree clean


Це підтвердило, що робоче дерево чисте, а локальна гілка main синхронізована з віддаленим репозиторієм.

10. Контрольні запитання
1. Чим .gitignore відрізняється від .gitattributes?

.gitignore визначає файли та каталоги, які Git не повинен додавати до індексу. Наприклад, це можуть бути локальні налаштування, тимчасові файли або секрети.

.gitattributes визначає атрибути файлів, наприклад спосіб обробки кінців рядків або те, що певний файл є бінарним.

2. Чому важливо переносити документи окремими комітами?

Окремі логічні коміти роблять історію зрозумілою. За кожним комітом можна визначити, яка саме частина документації була додана або змінена.

Це також спрощує пошук помилок і перегляд історії проєкту.

3. Коли Git виконує fast-forward?

Fast-forward можливий, коли поточна гілка не має власних нових комітів після створення іншої гілки. У такому випадку Git просто переміщує покажчик гілки вперед.

Якщо обидві гілки мають власні коміти, Git не може виконати fast-forward і може створити merge commit.

4. Що таке конфлікт злиття?

Конфлікт злиття виникає, коли Git не може автоматично визначити, яку з несумісних змін потрібно залишити. Найчастіше це трапляється, коли різні гілки змінюють один і той самий рядок файлу.

У такому випадку розробник повинен вручну вибрати або об'єднати потрібні зміни.

5. Як обирається спосіб скасування коміту?

Вибір залежить від того, чи був коміт опублікований.

Для локального коміту можна використовувати reset або amend, якщо потрібно змінити локальну історію.

Для вже опублікованого коміту доцільно використовувати revert, оскільки він створює новий коміт, який скасовує попередні зміни, не переписуючи історію.

6. Що станеться після git reset --hard до коміту, який уже завантажив інший учасник?

git reset --hard перемістить поточну гілку на вказаний коміт і видалить локальні зміни після нього. Якщо після цього виконати force push, віддалена історія буде переписана.

Це може створити проблеми для інших учасників, які вже завантажили попередню версію історії.

7. Що робить історію Git читабельною?

Читабельну історію забезпечують логічні та атомарні коміти, зрозумілі повідомлення комітів, правильне використання гілок і відсутність беззмістовних повідомлень на кшталт update, fix або wip.

Така історія спрощує командну розробку, пошук помилок, перегляд змін та розуміння етапів розвитку проєкту.

11. Висновок

Під час практичного заняття було налаштовано Git-репозиторій проєкту CoffeeGo та сформовано його базову структуру.

Було виконано роботу з .gitignore і .gitattributes, документацію попередніх практичних занять було організовано в окремих каталогах та логічних комітах.

Також було практично продемонстровано роботу з гілками, merge commit, конфліктом злиття та його ручним розв'язанням. Окремо було виконано скасування помилкової зміни та перевірено чистий стан робочого дерева.

У результаті отримано структурований Git-репозиторій із зрозумілою історією змін, який можна використовувати для подальшої розробки проєкту CoffeeGo.
