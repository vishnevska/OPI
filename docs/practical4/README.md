Мета роботи

Метою практичного заняття є набуття практичних навичок роботи з Git-репозиторієм: створення структури проєкту, налаштування .gitignore та .gitattributes, формування зрозумілої історії комітів, створення та злиття гілок, розв'язання конфліктів злиття та скасування помилкових комітів.

1. Створення репозиторію

Для проєкту «CoffeeGo» створено Git-репозиторій на GitHub.

Репозиторій містить документацію та базову структуру майбутнього програмного продукту.

Основний проєкт — мобільний застосунок для попереднього замовлення кави в мережі кав'ярень. Система передбачає мобільний застосунок для iOS та Android, REST API, базу даних PostgreSQL, Push-сповіщення та інтеграцію з POS-системою.

У README.md наведено опис призначення проєкту, основних можливостей, типу системи та користувачів.

3. Файли .gitignore та .gitattributes

Файл .gitignore використовується для виключення з репозиторію тимчасових файлів операційної системи, файлів IDE, локальних секретів та файлів, які генеруються .NET-проєктами.

Основні правила:

.DS_Store
Thumbs.db
.vscode/
.idea/
bin/
obj/
*.user
.env
appsettings.Development.json


Файл .gitattributes використовується для нормалізації текстових файлів та визначення бінарних файлів:

* text=auto

*.docx binary
*.pdf binary
*.png binary
*.jpg binary
*.jpeg binary


Таким чином, .gitignore визначає, які файли Git не повинен відстежувати, а .gitattributes визначає правила роботи Git із файлами, зокрема форматування кінців рядків та бінарні файли.

5. Робота з гілками та merge commit

Для виконання завдання було створено гілку:

docs/update-readme


У цій гілці було внесено доповнення до README.md.

Після створення гілки в main було зроблено окремий коміт. Таким чином, main та docs/update-readme мали різні зміни після спільної точки розгалуження.

Після цього гілку docs/update-readme було злито в main.

Оскільки основна гілка вже містила власний новий коміт, Git не міг виконати fast-forward. Було створено окремий merge commit із двома батьківськими комітами.

Після завершення злиття робочу гілку було видалено.

Це дозволило продемонструвати різницю між fast-forward злиттям та тристороннім злиттям із merge commit.

6. Створення та розв'язання конфлікту

Для демонстрації конфлікту було створено дві гілки:

feature/a
feature/b


В обох гілках було змінено один і той самий рядок у файлі README.md, але різними способами.

Після злиття feature/a у main зміни було прийнято без конфлікту.

Під час виконання:

git merge feature/b


Git повідомив:

Auto-merging README.md
CONFLICT (content): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.


Причиною конфлікту було те, що дві гілки змінили однакову ділянку файлу по-різному, тому Git не міг автоматично визначити, який варіант потрібно залишити.

У конфліктному файлі Git створює спеціальні маркери:

<<<<<<< HEAD
варіант із main
=======
варіант із feature/b
>>>>>>> feature/b


Після аналізу обох варіантів було обрано необхідний текст, маркери конфлікту видалено, після чого файл було додано до індексу командою:

git add README.md


Злиття було завершено комітом.

Таким чином, конфлікт було створено навмисно та успішно розв'язано вручну.

7. Скасування помилкового коміту

Для виконання цього завдання було навмисно створено тимчасовий файл temp.txt та виконано коміт:

chore: додати тимчасовий файл


Перед скасуванням було визначено, що цей коміт ще не був опублікований у віддаленому репозиторії.

Тому було використано:

git reset --soft HEAD~1


Команда reset була обрана тому, що помилковий коміт був лише локальним і його можна було безпечно прибрати з локальної історії.

Якби помилковий коміт уже був опублікований у спільному репозиторії, доцільніше було б використати git revert, оскільки він створює новий коміт, який скасовує попередні зміни, не переписуючи опубліковану історію.

Після скасування тимчасовий файл було видалено.

10. Контрольні запитання
1. Чим .gitignore відрізняється від .gitattributes?

.gitignore визначає файли та каталоги, які Git не повинен додавати до відстеження. .gitattributes визначає правила обробки вже відстежуваних файлів, наприклад нормалізацію кінців рядків або позначення файлів як бінарних.

2. Чому документи важливо переносити окремими комітами?

Окремі логічні коміти роблять історію репозиторію зрозумілою. За назвою та вмістом коміту можна швидко визначити, яку частину проєкту було змінено.

3. Коли Git виконує fast-forward?

Fast-forward можливий, коли поточна гілка не має власних нових комітів після створення іншої гілки. У такому випадку Git може просто перемістити вказівник гілки вперед без створення нового merge commit.

4. Що таке конфлікт злиття?

Конфлікт злиття виникає, коли різні гілки змінюють одну й ту саму частину файлу несумісними способами. Git не може сам визначити, який варіант правильний, тому користувач повинен вирішити конфлікт вручну.

5. Коли використовують reset, amend і revert?

reset можна застосовувати для скасування локальних комітів, які ще не були опубліковані. amend використовується для виправлення останнього коміту. revert використовується для скасування вже опублікованих змін без переписування історії.

6. Що станеться після git reset --hard для опублікованого коміту?

Локальна гілка буде переміщена назад, а зміни робочої директорії можуть бути безповоротно видалені. Якщо коміт уже є на віддаленому репозиторії, локальна та віддалена історії розійдуться. Примусовий push може створити проблеми для інших учасників команди.

7. Що робить історію Git читабельною?

Читабельну історію забезпечують невеликі логічні коміти, зрозумілі повідомлення, правильне використання гілок та відсутність зайвих або беззмістовних комітів. Це спрощує пошук змін, аналіз помилок та командну розробку.
