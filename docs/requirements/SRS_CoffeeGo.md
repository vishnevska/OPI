# Технічне завдання (SRS) — CoffeeGo

## 1. Вступ

### 1.1. Мета документа

Цей документ описує програмні вимоги до мобільного застосунку та бек-офісу мережі кав'ярень «CoffeeGo».

Документ призначений для команди розробки, QA-інженерів, UI/UX дизайнера та замовника.

### 1.2. Область застосування

Програмний продукт включає:

- кросплатформений мобільний застосунок для iOS та Android;
- планшетний інтерфейс для баристи;
- серверний модуль інтеграції з POS-системою кав'ярні.

### 1.3. Основні функції

Система повинна забезпечувати:

- перегляд меню та актуальних цін;
- формування попереднього замовлення;
- онлайн-оплату;
- вибір часу отримання замовлення;
- накопичення та використання бонусних балів;
- Push-сповіщення про готовність замовлення;
- перегляд та зміну статусів замовлень баристою;
- перегляд замовлень менеджером;
- інтеграцію з POS-системою.

## 2. Загальний опис

### 2.1. Тип системи

CoffeeGo — мобільний комплекс попереднього замовлення кави:

- Mobile — iOS / Android;
- Web API — серверна частина;
- Tablet UI — інтерфейс баристи.

### 2.2. Користувачі

**Клієнт** — переглядає меню, формує та оплачує замовлення.

**Бариста** — переглядає замовлення та змінює їх статус.

**Менеджер** — контролює замовлення та отримує звіти.

### 2.3. Цілі проєкту

- зменшити середній час очікування клієнта з 15 хвилин до менше ніж 3 хвилин;
- забезпечити оформлення не менше 30% ранкових замовлень через застосунок протягом 30 днів після релізу;
- забезпечити запуск першої версії до 1 грудня.

## 4. Нефункціональні вимоги

### Продуктивність

Час відповіді API-запитів для каталогу та замовлень не повинен перевищувати 300 мс на 95-му перцентилі при навантаженні до 500 одночасних користувачів.

### Надійність

Доступність системи повинна становити не менше 99,5% на місяць.

### Безпека

Передача даних повинна здійснюватися через HTTPS із використанням TLS 1.3.

Автентифікація користувачів повинна використовувати JWT-токени.

Паролі повинні зберігатися у хешованому вигляді.

### Зручність використання

Мобільний застосунок повинен підтримувати смартфони з діагоналлю від 4.7" до 6.8".

Інтерфейс баристи повинен бути оптимізований для планшетів.

- інтеграція з наявною POS-системою;
- строк релізу — до 1 грудня.

## 6. Критерії прийнятності

### Сценарій 1 — оформлення та оплата

**Given:** клієнт сформував кошик на суму 100 грн та обрав час видачі 08:30.

**When:** клієнт підтверджує оплату через Apple Pay.

**Then:** застосунок показує номер замовлення та час видачі, а замовлення передається в POS-систему зі статусом «Оплачено».

### Сценарій 2 — готовність замовлення

**Given:** замовлення перебуває у статусі «В процесі».

**When:** бариста натискає кнопку «Готово».

**Then:** клієнт отримує Push-сповіщення про готовність замовлення.

### Сценарій 3 — помилка оплати

**Given:** на картці клієнта недостатньо коштів.

**When:** клієнт намагається оплатити замовлення.

**Then:** система показує повідомлення про помилку, не передає замовлення баристі та залишає товари у кошику.

## 7. Definition of Done

Реліз вважається готовим, якщо:

- усі Must-вимоги реалізовані;
- Acceptance-тести успішно пройдені;
- відсутні критичні дефекти;
- виконано перевірку продуктивності та безпеки;
- код пройшов Code Review;
- підготовлена необхідна документація;
- проведена демонстрація замовнику.
